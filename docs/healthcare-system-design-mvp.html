Method

Facts, hypotheses, and decisions stay separate.

The system and this design use the same discipline: supplied information is not promoted to fact without evidence, and popular architecture patterns are not selected without experiments.

Selected

A reversible choice with a reason, experiment evidence, and reversal condition.

Scope rule. The MVP maps responsibilities and cheapest discriminating tests. It does not pretend that a diagram proves orchestration, memory, self-correction, platform expertise, or migration correctness.

Logical architecture · Technology neutral

Apex reasoning around durable state, independent proof, and bounded execution.

Workers reason. Product-owned state records what is known and decided. Independent evaluation decides acceptance. Effect gates constrain real actions. Technology and deployable boundaries remain open.

Core operating loop

Discover first. Decide from evidence. Execute only after proof is defined.

Loose outcomeCapture desired result, access, priorities, and known exceptions.
DiscoverInspect systems, data, code, behavior, history, and target constraints.
Model estateRecord facts, claims, provenance, dependencies, and freshness.
Find gapsDetect contradictions, unknowns, hidden assets, and unsupported assumptions.
ResolveRetrieve, compare, probe, experiment, or ask a specialist.
Decide & planChoose technical and functional path plus proof and recovery obligations.
Build & evaluateGenerate artifacts and independently test before mutation.
Execute & reconcileBound effects, read target state, handle unknown outcomes.
LearnRetain accepted evidence; revise or demote failed knowledge and skills.

Gap-resolution decision tree

Is the claim directly observed and current?
YesRecord evidence, applicability, and freshness.
NoKeep it as a claim or hypothesis.
ConflictCreate an explicit contradiction gap.
Can trusted retrieval resolve the gap?
YesCite source/version and test local applicability.
NoInspect code, data, logs, and consumers.
Stale sourceDo not silently apply it.
Can a safe probe separate the hypotheses?
YesRun the cheapest discriminating experiment.
NoAsk independent specialists and compare evidence.
RiskyDesign a safer proxy or sandbox case.
Is one path now materially better supported?
YesDecide, prove, record, and continue.
True tieEscalate the smallest irreducible question.
Unknown riskQuarantine affected scope; unrelated work continues.
Deliverable 1 · System component map

Twenty-four responsibilities with explicit inputs, outputs, state, and failure edges.

These are logical components. Several may live in one process; one may later split. The MVP deliberately avoids choosing deployables.

SYS-01 · Interaction

Mission intake and operator console

Hypothesis

Captures loose outcomes and shows discovered reality, gaps, decisions, evidence, execution, and exceptions.

Inputs
Goals, access, artifacts, priorities, exceptions.
Outputs
MissionBrief, operator views, exception replies.
State owner
None; reads/writes through mission APIs.
Failure edge
Bad customer input remains an unverified claim.
SYS-02 · Control

Mission and estate model

State owner

Maintains the current evidence-backed picture of systems, assets, dependencies, claims, scope, and objectives.

Inputs
Mission brief, evidence observations, decisions.
Outputs
EstateSnapshot, scoped mission projections.
State owner
Mission/estate records and versions.
Failure edge
Projection can be stale; evidence history remains reconstructable.
SYS-03 · Control

Apex mission controller

Core hypothesis

Chooses the next highest-value discovery, research, build, validation, execution, or recovery action.

Inputs
Mission state, gaps, evidence, budgets, results.
Outputs
Assignments, decisions, revised plan.
State owner
None; working context is disposable.
Failure edge
Cannot directly accept results or execute effects.
SYS-04 · Control

Gap and hypothesis engine

Hypothesis

Types facts, claims, contradictions, hypotheses, open questions, and disproven assumptions.

Inputs
Evidence, research, specialist results.
Outputs
GapRecord, ranked hypotheses, test requests.
State owner
Gap/hypothesis records through mission state.
Failure edge
Untracked uncertainty becomes false certainty.
SYS-05 · Control

Plan and DAG compiler

Hypothesis

Turns current decisions into bounded tasks with dependencies, proof obligations, budgets, and recovery rules.

Inputs
Decisions, skills, estate version, policy.
Outputs
PlanGraph, validation errors.
State owner
Immutable plan versions.
Failure edge
Invalid or incomplete plans remain non-runnable.
SYS-06 · Control

Durable workflow ledger and reconciler

State owner

Owns tasks, attempts, leases, transitions, effects, receipts, evaluation gates, and recovery after restart.

Inputs
Validated plans, worker observations, evaluator verdicts.
Outputs
Runnable attempts, accepted transitions, recovery work.
State owner
Workflow and effect history.
Failure edge
No other component may advance workflow truth.
SYS-07 · Control

Policy and effect gate

State owner

Checks tenant, identity, expected state, skill, tool, scope, budget, expiry, and fencing before effects.

Inputs
EffectIntent, plan, policy, active attempt.
Outputs
CapabilityEnvelope or deterministic rejection.
State owner
Policy versions and authorization decisions.
Failure edge
Models and tools cannot grant themselves authority.
SYS-08 · Intelligence

Context assembler

Hypothesis

Builds a bounded, tenant-scoped, cited context for one assignment from current state and allowed knowledge.

Inputs
Assignment, estate version, corpus, memory, skills.
Outputs
ContextManifest.
State owner
Context manifest only; no source ownership.
Failure edge
Cross-tenant, stale, or uncited context invalidates work.
SYS-09 · Intelligence

Specialist agent pool

Untrusted worker

Runs source forensics, architecture, CDC, mapping, domain, security, research, build, evaluation, and recovery specialists.

Inputs
AgentAssignment, context, allowed tools.
Outputs
AgentResult, evidence refs, gaps.
State owner
Disposable OMP/session state.
Failure edge
Outputs are proposals until independently checked.
SYS-10 · Intelligence

Model router and gateway

Hypothesis

Selects approved models by task, data class, capability, cost, latency, and evaluator separation.

Inputs
Assignment policy, data classification, model telemetry.
Outputs
Bound model invocation and usage evidence.
State owner
Model policy and measured capability matrix.
Failure edge
Fallback cannot weaken data or evaluator policy.
SYS-11 · Knowledge

Research and retrieval service

Research

Retrieves current primary sources, known answers, analogous cases, and contradictory material with citations.

Inputs
ResearchRequest, access policy, query context.
Outputs
ResearchResult, citations, coverage gaps.
State owner
Search traces, not source truth.
Failure edge
Retrieval relevance does not prove local applicability.
SYS-12 · Knowledge

Versioned reference corpus

State owner

Stores approved vendor docs, standards, schemas, examples, runbooks, cases, and benchmark fixtures.

Inputs
Acquired sources with owner, license, class, version.
Outputs
Citable source versions and corpus manifests.
State owner
Reference artifacts and metadata.
Failure edge
Stale, unlicensed, or unscoped items are excluded.
SYS-13 · Knowledge

Knowledge and evidence index

Storage open

Projects entities, relationships, time, versions, provenance, and retrieval indexes over corpus and evidence.

Inputs
Corpus metadata, observations, accepted decisions.
Outputs
Scoped graph/text/vector queries.
State owner
Rebuildable indexes and typed projections.
Failure edge
Index answers must resolve back to source evidence.
SYS-14 · Knowledge

Memory manager

Research

Manages mission, episodic, semantic, procedural, failure, and evaluation memory with provenance and invalidation.

Inputs
Accepted run traces, corrections, failures, explicit lessons.
Outputs
Scoped memory candidates and recall traces.
State owner
Non-authoritative memory records.
Failure edge
Poisoned or stale memory cannot silently become fact.
SYS-15 · Knowledge

Skill and capability registry

State owner

Owns versioned executable skills, supported envelope, tools, evaluators, benchmark status, promotion, and demotion.

Inputs
SkillManifest, benchmark and production evidence.
Outputs
Assignable skill versions and revocations.
State owner
Skill lifecycle and compatibility state.
Failure edge
A prompt file alone is never certified capability.
SYS-16 · Engineering

Discovery coordinator

Hypothesis

Plans least-privilege inventory, profiling, code analysis, lineage, operational, and contradiction-discovery work.

Inputs
Mission scope, current estate, source capabilities.
Outputs
Probe assignments and coverage report.
State owner
Discovery coverage projection.
Failure edge
Access denial is not evidence that an asset is absent.
SYS-17 · Engineering

Source adapters and probe sandbox

Build / reuse

Executes version-aware reads, metadata scans, profiles, traces, code extraction, and bounded experiments near sources.

Inputs
Probe plan, temporary credential, source contract.
Outputs
EvidenceObservation, artifacts, denials, errors.
State owner
None; local bounded spool only.
Failure edge
Source quirks remain adapter-specific and testable.
SYS-18 · Engineering

Artifact builder and target designer

Hypothesis

Creates target architecture, mappings, pipeline code, infrastructure, tests, runbooks, and migration packages.

Inputs
Compiled decisions, estate snapshot, target capability, skills.
Outputs
Versioned reproducible artifacts and provenance.
State owner
Artifact metadata; bodies in evidence store.
Failure edge
Generated output is rejected if it cannot build or prove contracts.
SYS-19 · Engineering

Execution broker, relay, and sandbox

Critical boundary

Routes leased work to isolated customer-zone tools, stages artifacts, leases secrets, and returns signed receipts.

Inputs
Capability envelope, artifacts, execution provider.
Outputs
Runner observations, receipts, evidence chunks.
State owner
No mission authority; bounded encrypted spool.
Failure edge
Partition and timeout create explicit unknown outcomes.
SYS-20 · Engineering

Target adapters and reconcilers

Build / reuse

Performs selected platform operations and independently reads target identity and state after success or uncertainty.

Inputs
Effect envelope, target credential lease, expected state.
Outputs
EffectReceipt, target readback, unknown status.
State owner
None; target remains external reality.
Failure edge
No blind retry after a possibly applied write.
SYS-21 · Assurance

Evaluation coordinator

State owner

Assigns independent checks against pinned inputs, thresholds, evaluators, and protected invariants.

Inputs
Subject artifact/effect, evaluator contract, evidence.
Outputs
EvaluationResult and acceptance coverage.
State owner
Evaluation assignments and verdict history.
Failure edge
Missing or contradictory evaluation keeps subject unaccepted.
SYS-22 · Assurance

Deterministic evaluators

Preferred oracle

Runs schema, contract, build, replay, control-total, lineage, target-readback, property, and fault checks.

Inputs
Exact subject and fixture versions.
Outputs
Measures, failures, reproducible evidence.
State owner
None; results owned by evaluation coordinator.
Failure edge
Evaluator defects require their own regression corpus.
SYS-23 · Assurance

Semantic and expert-calibrated evaluators

Research

Evaluates meaning where deterministic checks are insufficient, using held-out labels, disagreement rules, and calibration.

Inputs
Semantic cases, subject output, independent context.
Outputs
Measures, disagreement, abstention, evidence.
State owner
Evaluator version and calibration records.
Failure edge
Producer self-review cannot substitute.
SYS-24 · Assurance

Evidence and artifact store

State owner

Stores immutable observations, inputs, generated artifacts, receipts, evaluations, failures, provenance, and integrity metadata.

Inputs
Evidence bodies, artifact metadata, digests, classifications.
Outputs
Citable versioned evidence references.
State owner
Evidence metadata and immutable bodies.
Failure edge
Missing required evidence prevents acceptance.

MVP review gate

Review the cuts before adding detail.

The next iteration should not add more components or technologies until these questions are answered.

Questions for review

  • Are any two components secretly the same responsibility?
  • Is any state owner missing or ambiguous?
  • Can the apex controller be replaced without losing mission continuity?
  • Does every real effect have an independent reconciliation path?
  • Are the first 12 experiments sufficient to choose the major architecture cuts?
  • Which corpus candidates give the most learning per setup hour?

Stop conditions

  • Do not build the full migration demo before atomic experiments.
  • Do not lock graph storage, workflow engine, language, bus, or deployment topology from diagrams.
  • Do not treat OMP memory, agent output, or customer artifacts as facts.
  • Do not add a framework without naming the exact capability and experiment it replaces.
  • Do not call a skill self-improving until regression and demotion work.

Proposed next small step after review

Build only Phase 0 evidence. Create six deeper research cards—durable workflow, apex orchestration, memory, knowledge retrieval, evaluation, and connector/sandbox—and refine EXP-01, EXP-05, EXP-07, EXP-08, EXP-10, and EXP-11 into executable lab specs. No end-to-end migration yet.
