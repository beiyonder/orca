Technical design · Requirements before solutions

The architecture follows the work, failure model, and data—not framework fashion.

Non-functional requirements and invariants

Data locality

Raw migration data moves within customer execution zones. The control plane stores metadata, bounded samples, artifacts, and proof—not the bulk data path.

Per-aggregate correctness

Mission, task, attempt, and effect transitions use expected versions and transactions. No global exactly-once claim.

At-least-once transport

Commands and receipts may duplicate. Inbox keys, effect identity, fencing, and target reconciliation make duplication safe.

Replaceable intelligence

Models and OMP workers can crash, change, or be replaced without losing mission state or granting authority.

Tenant and data-class isolation

Tenant, environment, classification, and policy travel with every context, artifact, tool, memory, and effect.

Evidence before acceptance

Missing object bodies, failed evaluators, stale target reads, or unknown effects keep work unaccepted.

Recover before retry

A timed-out external write becomes unknown. The system reads target reality before deciding retry, repair, or quarantine.

Simple until measured

One PostgreSQL authority, no initial message bus, no graph database, and no cache without a measured bottleneck or query need.

Baseline recommendation. Start with a modular control plane, PostgreSQL transactional authority and work queues, S3-compatible evidence storage, one Bun OMP RPC gateway, and outbound customer-zone execution relays. Add a dedicated workflow engine, message bus, graph database, or cache only when an experiment or load measurement names the gap.

Feedback loops

Reinforcing

Proof compounds capability

Better corpus → better decisions → more accepted runs → better cases and skills → better decisions. This is the desired moat.

Balancing

Evaluation limits bad growth

Regression → failed evaluator → assignment stop → demotion → rollback → re-certification. This prevents capability claims from outrunning proof.

Dangerous

Confident output poisons memory

Wrong output → automatic retention → repeated retrieval → stronger wrong belief. Candidate memory quarantine breaks this loop.

Delay

Real outcomes arrive late

Migration defects may surface after backfill, CDC, cutover, or downstream use. The evidence model must keep old decisions linked and reversible.

Leverage

Gap policy

The next-action policy determines whether the system investigates reality or cheaply generates plans from weak inputs.

Leverage

Evaluator quality

Improving the oracle has more system-wide value than adding another generator model. Bad evaluators corrupt promotion, memory, and decisions.

Technical design · Protocols and consistency

At-least-once messages, per-aggregate serial transitions, and explicit unknown effects.

The system avoids distributed exactly-once claims. It uses database transactions where one database can decide, then identity, idempotency, leases, fencing, receipts, and reconciliation across process and network boundaries.

Freedom boundary

Adaptive

Reasoning and replanning

The apex may change hypotheses, investigations, specialists, tools, architecture, mappings, task decomposition, dependencies, priorities, and plan shape whenever new evidence warrants it.

Deterministic

Authority and acceptance

The kernel enforces current versions, tenant/scope, legal transitions, idempotency, fences, effect identity, evidence integrity, independent evaluation, and immutable history.

Platform health

PostgreSQL commit/replication lag, object latency/errors, gateway RSS, relay reconnects, runner saturation.

Safety before liveness. During uncertainty, the architecture may stop affected progress. It must not accept unsupported state, reuse stale authority, lose required evidence, or duplicate an external mutation to keep throughput green.

MVP review gate

Attack the technical baseline before implementation.

The architecture is now concrete enough to falsify. The next discussion should challenge load assumptions, transaction boundaries, service cuts, failure behavior, security, operability, and cost.

Questions for review

  • Does raw data truly stay out of the control plane for every required workflow?
  • Are the planning values—50 missions, 100 agents, 10M events/year, 1–20 TB evidence—useful first envelopes?
  • Can PostgreSQL outbox/leases carry the initial workload without Temporal or a message bus?
  • Are eight deployables the minimum useful failure boundaries?
  • Are REST/SSE, OMP JSONL, and outbound relay streams the right protocol cuts?
  • Does every real effect have a stable identity and target reconciliation path?
  • Can the knowledge/memory design prove provenance, isolation, expiry, and harm?
  • Which customer SLO/RTO/RPO assumptions would reverse this architecture?

Stop conditions

  • Do not build the full migration demo before atomic experiments.
  • Do not promote Go, PostgreSQL, Kubernetes, WebSocket, or the custom reconciler from baseline to locked without measurements.
  • Do not add Temporal, NATS/Kafka, Redis, a graph database, or more services without naming the pressure they remove.
  • Do not treat OMP memory, agent output, customer artifacts, or derived indexes as authoritative facts.
  • Do not let RPC success, message delivery, runner exit, or a receipt alone mean accepted work.
  • Do not call a skill self-improving until regression, demotion, and rollback work.
